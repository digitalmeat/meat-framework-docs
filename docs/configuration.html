Introduction

All configuration files for MEAT Framework live in the config/ directory at project root. Each file is dedicated to a feature or package (application, cache, database, WordPress, …). Sensitive values are never stored in config files — they live in a .env file managed by the vlucas/phpdotenv package.

Environment configuration (.env)

Environment variables are defined in a single .env file at project root. This file keeps critical data (passwords, API keys, salts) out of the web-server public root and out of version control. A .env.sample file is committed to the repo as the template.

Copy it on first install:

cp .env.sample .env

Default variables

APP_ENV=local
APP_DEBUG=false
APP_KEY=
APP_TD=my-app

# WordPress salts — generate with: php artisan salts:generate
AUTH_KEY=
SECURE_AUTH_KEY=
LOGGED_IN_KEY=
NONCE_KEY=
AUTH_SALT=
SECURE_AUTH_SALT=
LOGGED_IN_SALT=
NONCE_SALT=

APP_URL=http://local.test
WP_URL=http://local.test/cms

DATABASE_NAME=my_db
DATABASE_USER=root
DATABASE_PASSWORD=root
DATABASE_HOST=localhost
DATABASE_PREFIX=wp_

MAIL_HOST=smtp.mailtrap.io
MAIL_USERNAME=null
MAIL_PASSWORD=null
MAIL_FROM_ADDRESS=noreply@example.com
MAIL_FROM_NAME=MEAT Framework
APP_URL is the base URL of your application. WP_URL is the WordPress admin URL — WordPress is installed in the cms/ subdirectory by default, so keep the /cms fragment.

If APP_ENV is removed, it defaults to production. Leave APP_DEBUG=false until WordPress is fully installed — PHP 8.x compatibility warnings from WordPress itself will otherwise flood the screen.

Reading environment values

Values from .env are loaded by vlucas/phpdotenv into $_ENV and $_SERVER. Use the env() helper anywhere in your code: 

$debug = env('APP_DEBUG');

// With a default
$custom = env('MY_VAR', 'default');

Detecting the current environment

use Illuminate\Support\Facades\App;

$env = App::environment(); // 'local', 'staging', 'production'…

if (App::environment('local')) {
 // local only
}

if (App::environment(['local', 'staging'])) {
 // local or staging
}

WordPress configuration

Instead of editing wp-config.php, all WordPress constants go in config/wordpress.php. This file has access to env() and all illuminate/config helpers: 

// config/wordpress.php
define('WP_DEBUG', env('APP_DEBUG', false));
define('WP_DEBUG_LOG', env('APP_DEBUG', false));
define('DISALLOW_FILE_EDIT', true);

Salt and nonce keys

Generate WordPress authentication keys and salts:

php artisan salts:generate

This writes values to your .env and maps them in config/wordpress.php:

define('AUTH_KEY', config('app.salts.auth_key'));
define('SECURE_AUTH_KEY', config('app.salts.secure_auth_key'));
define('LOGGED_IN_KEY', config('app.salts.logged_in_key'));
define('NONCE_KEY', config('app.salts.nonce_key'));
// …

Accessing configuration values

Configuration is managed by the illuminate/config package. Use the config() helper or the Config facade: 

// Via helper
$name = config('app.name');
$name = config('app.name', 'My App'); // with default

// Via facade
use Illuminate\Support\Facades\Config;
$charset = Config::get('app.charset');

The dot syntax maps to file + key: app.name → config/app.php → name key.

// Retrieve a nested value
$wpDir = config('app.wp.dir');

// Retrieve all properties of a config file
$all = config('theme'); // all keys from config/theme.php

Configuration load order

If multiple config files share the same name (root, plugin, theme), they do not merge. Load order: root config → active plugins → active theme, with later loaders overriding earlier ones. Use unique filenames per plugin/theme to avoid unexpected overrides.
